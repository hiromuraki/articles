## 1. 问题一：8010 / 8020 从 Windows 无法访问（11/2）

### 1.1. 现象

| 检查项                                 | 结果                                 |
| -------------------------------------- | ------------------------------------ |
| WSL 内 `ss -tlnp`                      | `docker-proxy` 监听 `127.0.0.1:8010` |
| WSL 内 `curl 127.0.0.1:8010`           | **HTTP 200**（服务正常）             |
| Windows `netstat`                      | 完全没有 8010 的监听                 |
| Windows `curl 127.0.0.1:8010`          | 连接被拒（exit 7）                   |
| Windows → WSL IP `172.22.176.178:8010` | 失败（服务只绑 loopback）            |
| Windows → WSL IP `:22`、`:18080`       | 正常（证明网络通路和防火墙没问题）   |
| 29380 / 6099                           | 当时正常                             |

`compose.yml` 中 computer 与 web-search 的端口发布写法：

```yaml
- "127.0.0.1:8010:8000"   # computer
- "127.0.0.1:8020:8000"   # web-search
```

### 1.2. 根因

**Windows 把 8010/8020 划进了「排除端口段」（excluded port range）**，任何进程都绑不上，包括 WSL 的转发进程 `wslrelay.exe`。

```text
7962  - 8061   ← 包含 8010
8062  - 8161   ← 包含 8020
```

直接证据：在 Windows 上尝试 bind `127.0.0.1:8010`，返回：

```text
WSAEACCES (10013) — 以一种访问权限不允许的方式做了一个访问套接字的尝试
```

对照端口 `18011` 可以正常 bind。

这些排除段由 **HNS（Host Network Service，主机网络服务）** 在每次 Windows 启动/网络重建时，从 TCP 动态端口范围里随机划走，通常 100 个端口一块。预留 ≠ 监听，所以 `netstat` 看不到，但 bind 会失败。

**为什么能划到 8000 这种开发常用段？** 因为这台机器的 TCP 动态端口范围被改宽了：

| 项目                     | Windows 默认            | 本机实际                   |
| ------------------------ | ----------------------- | -------------------------- |
| IPv4 TCP 动态端口范围    | 49152–65535（16384 个） | **1024–65534（64511 个）** |
| IPv6 TCP 动态端口范围    | 49152–65535（16384 个） | **1024–65534（64511 个）** |
| IPv4 UDP 动态端口范围    | 49152–65535             | 49152–65535（默认，未改）  |
| `MaxUserPort`            | 不存在（不创建）        | **65534**                  |
| `StrictTimeWaitSeqCheck` | 不存在 / 等效 0         | **1**                      |

`MaxUserPort=65534` 是历史遗留的 TCP 调优值。在 Windows 11 上它的效果是：起始端口 1024、结束端口 `MaxUserPort`，数量 = 65534 − 1024 + 1 = **64511**，与实测完全一致。它把 8000 段放进了 HNS 的候选池。

### 1.3. 关于 `MaxUserPort` 的来源（取证结果）

- 加载了 `C:\Windows.old` 里 **10/31 原地升级前**的旧 SYSTEM hive，确认升级前就已经存在：
  - `MaxUserPort=65534`
  - `StrictTimeWaitSeqCheck=1`
  - `PortTrackerEnabledMode=2`
- 所以**不是 10/31 的 Windows 升级写的**，也不是最近两天写的。
- **已排除 Wireshark / Npcap**：安装目录无相关引用，Npcap 不修改 TCP 端口范围。
- **已排除 Clash Verge**：日志里的 “65534” 只是代理连接的临时端口。
- 剩余可能是雷神加速器（8/30 安装）、UU 加速器（4/26 安装）或更早的“网络优化”脚本；这类工具常写同一套 `MaxUserPort + StrictTimeWaitSeqCheck`。**无法 100% 归因**。
- **精确写入日期不可考**：Windows 注册表不记录单个值的写入时间；键级时间被睡眠恢复/DHCP 刷新污染；没有 Sysmon、没有 4657 注册表审计；`RegBack` 为空；没有还原点；Shell 历史里也没有相关命令。
- 取证用的 `OLD_SYSTEM` hive 已卸载，临时副本已删除，未残留。

### 1.4. 为什么“值很旧、故障很新”

`MaxUserPort` 只是让 8000 段**有资格**被 HNS 抽中。真正的故障时刻是 10/31 升级重启后，HNS 重新随机划走了 `7962–8161`。值可以是几个月前写的，抽中 8010 只需要一次重启。10/31 的 Windows Insider 原地升级（安装 `KB5127719`，21:27 重启，21:31 完成）+ WSL 重启，就是这次抽签的触发点。

### 1.5. 已做的临时处理

```text
WSL 0.0.0.0:18010  →  WSL 127.0.0.1:8010
```

- 手动运行 `wslrelay.exe` 无效——它需要 WSL 服务传入内部参数，会立即退出。

这是已知的 wslrelay 回归类问题，不是 8010 的端口排除问题。

然后正常启动 Ubuntu（打开终端，或执行 `wsl -d Ubuntu`）。

## 4. 附录：`fwd8010.py`

```python
import asyncio

TARGET = ("127.0.0.1", 8010)
LISTEN = ("0.0.0.0", 18010)

async def pipe(reader, writer):
    try:
        while True:
            data = await reader.read(65536)
            if not data:
                break
            writer.write(data)
            await writer.drain()
    except Exception:
        pass
    finally:
        try:
            writer.close()
        except Exception:
            pass

async def handle(reader, writer):
    try:
        t_reader, t_writer = await asyncio.open_connection(*TARGET)
    except Exception:
        try:
            writer.close()
        except Exception:
            pass
        return
    await asyncio.gather(pipe(reader, t_writer), pipe(t_reader, writer))

async def main():
    server = await asyncio.start_server(handle, *LISTEN)
    async with server:
        await server.serve_forever()

asyncio.run(main())
```

## 5. 背景知识：HNS 和默认值

- **HNS（Host Network Service，主机网络服务）**：Windows 自带服务 `hns`，是容器/虚拟机网络栈的管理层。WSL2 的 NAT 网络、Hyper-V、Docker/Podman 的容器网络都靠它。它与 `vmcompute`（Hyper-V 主机计算服务）、`winnat`（Windows NAT 驱动）配合。
- HNS 为 NAT 预留宿主端口时，会从 TCP 动态端口范围里按 100 个一块随机划走，显示在 `netsh int ipv4 show excludedportrange` 里。预留不是监听，所以 `netstat` 看不到，但 bind 会报 `WSAEACCES (10013)`。
- Windows Vista+ 默认动态端口范围是 **49152–65535（16384 个）**，TCP/UDP、IPv4/IPv6 各自独立。
- `MaxUserPort` 是 Windows 2000/XP/2003 时代的遗留值，默认不存在；在现代 Windows 上它会把动态范围拉宽到 1024–65534，反而让开发端口进入抽签池。
- `StrictTimeWaitSeqCheck=1` 是配合 `TcpTimedWaitDelay` 的旧调优值，默认不存在/等效 0。
- `PortTrackerEnabledMode` 与 WSL 的 FSE 端口跟踪驱动相关（本机 FSE 正在运行，属正常）。
